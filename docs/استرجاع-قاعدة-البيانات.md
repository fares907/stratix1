# استرجاع قاعدة البيانات

دليل استرجاع نسخة احتياطية لموقع STRATIX. اقرأه بالكامل قبل أن تنفّذ أي خطوة.

> **قاعدة واحدة لا تُخالَف:** لا تسترجع فوق قاعدة البيانات العاملة مباشرة.
> ملف النسخة يبدأ بـ `DROP TABLE IF EXISTS`، أي أنه **يمسح الجداول الموجودة**
> قبل أن يكتب مكانها. إذا كانت النسخة قديمة أو ناقصة، تكون قد استبدلت بيانات
> صحيحة ببيانات أسوأ، ولا سبيل للرجوع. استرجع دائماً إلى قاعدة منفصلة أولاً.

---

## ما تحتاجه قبل البدء

| المتطلب | من أين |
|---|---|
| ملف النسخة الاحتياطية | GitHub → Actions → Database backup |
| كلمة سر التشفير | `BACKUP_PASSPHRASE` — المكان الآمن الذي حفظتها فيه |
| بيانات الاتصال | `DATABASE_URL` من متغيرات Railway |
| أداة `mysql` و `openssl` | مثبّتة على جهازك |

بدون كلمة السر لا يمكن فتح النسخة. لا أحد يستطيع استخراجها — لا GitHub ولا أي جهة أخرى.

---

## الخطوة 1 — نزّل النسخة

1. افتح **[صفحة النسخ الاحتياطي](https://github.com/fares907/stratix1/actions/workflows/backup.yml)**
2. اختر التشغيل الناجح المناسب للتاريخ الذي تريده (علامة ✅ خضراء)
3. انزل إلى أسفل الصفحة عند قسم **Artifacts**
4. اضغط على `db-backup-YYYY-MM-DD` — سينزل كملف مضغوط
5. فك الضغط، ستجد بداخله ملفاً ينتهي بـ `.sql.gz.enc`

النسخ تُحفظ **90 يوماً**. الأقدم من ذلك يُحذف تلقائياً.

---

## الخطوة 2 — فك التشفير

```bash
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 \
  -in db-backup-2026-08-16.sql.gz.enc \
  -out backup.sql.gz
```

سيطلب منك كلمة السر. اكتبها — لن تظهر على الشاشة أثناء الكتابة، وهذا طبيعي.

**إذا ظهرت رسالة `bad decrypt`** فكلمة السر خاطئة. الملف سليم، والمشكلة في الكلمة فقط.

---

## الخطوة 3 — فك الضغط

```bash
gunzip backup.sql.gz
```

النتيجة ملف `backup.sql`.

---

## الخطوة 4 — تحقّق قبل أن تلمس أي قاعدة بيانات

**لا تتخطَّ هذه الخطوة.** استرجاع نسخة ناقصة أسوأ من عدم الاسترجاع.

```bash
# هل الجداول الثلاثة موجودة؟
grep '^CREATE TABLE' backup.sql

# كم عدد صفوف البيانات؟
grep -c '^INSERT INTO' backup.sql

# هل اكتملت النسخة؟ يجب أن تنتهي بسطر "Dump completed"
tail -1 backup.sql
```

يجب أن ترى `bookings` و `ledgerEntries` و `users`. إذا نقص أي منها، **استخدم نسخة أقدم** ولا تكمل.

---

## الخطوة 5 — استرجع إلى قاعدة منفصلة أولاً

هنا تتجنّب الكارثة: تسترجع إلى قاعدة جديدة فارغة، لا إلى العاملة.

جهّز بيانات الاتصال من `DATABASE_URL` (شكلها: `mysql://المستخدم:كلمةالسر@المضيف:4000/test`).

```bash
# أنشئ قاعدة مؤقتة للفحص
mysql --host=gateway01.eu-central-1.prod.aws.tidbcloud.com \
      --port=4000 \
      --user=<المستخدم> \
      --password \
      --ssl-mode=VERIFY_IDENTITY \
      -e "CREATE DATABASE restore_check;"

# استرجع النسخة إليها
mysql --host=gateway01.eu-central-1.prod.aws.tidbcloud.com \
      --port=4000 \
      --user=<المستخدم> \
      --password \
      --ssl-mode=VERIFY_IDENTITY \
      restore_check < backup.sql
```

---

## الخطوة 6 — افحص البيانات المسترجعة

```bash
mysql --host=gateway01.eu-central-1.prod.aws.tidbcloud.com \
      --port=4000 --user=<المستخدم> --password \
      --ssl-mode=VERIFY_IDENTITY restore_check \
      -e "SELECT COUNT(*) AS حجوزات FROM bookings;
          SELECT publicId, name, phone, createdAt FROM bookings ORDER BY createdAt DESC LIMIT 5;
          SELECT COUNT(*) AS قيود FROM ledgerEntries;"
```

اسأل نفسك: هل عدد الحجوزات منطقي؟ هل آخر حجز قريب من التاريخ المتوقع؟

**إذا لم تكن البيانات كما تتوقع، توقّف هنا** وجرّب نسخة من تاريخ آخر. لم تُمسّ قاعدة البيانات العاملة حتى الآن.

---

## الخطوة 7 — التبديل

بعد أن تتأكد أن البيانات صحيحة، أمامك خياران:

### الخيار الآمن (المفضّل)

لا تنقل شيئاً. غيّر `DATABASE_URL` في Railway ليشير إلى `restore_check` بدل `test`، ثم أعد تشغيل الخدمة. القاعدة القديمة تبقى كما هي، فإن ظهر خطأ ترجع إليها فوراً.

### الخيار المباشر

استرجع فوق القاعدة الأصلية:

```bash
mysql --host=... --user=<المستخدم> --password \
      --ssl-mode=VERIFY_IDENTITY test < backup.sql
```

**هذا يمسح كل ما في `test` حالياً.** لا تفعله إلا إذا كنت متأكداً أن ما فيها ضائع أو تالف بالفعل.

---

## بعد الانتهاء

احذف القاعدة المؤقتة عندما تنتهي منها:

```bash
mysql --host=... --user=<المستخدم> --password \
      --ssl-mode=VERIFY_IDENTITY -e "DROP DATABASE restore_check;"
```

واحذف `backup.sql` من جهازك — فهو يحتوي أسماء عملائك وأرقام هواتفهم وبريدهم الإلكتروني بدون أي تشفير.

---

## أخطاء شائعة

| الرسالة | السبب | الحل |
|---|---|---|
| `bad decrypt` | كلمة السر خاطئة | تأكد من `BACKUP_PASSPHRASE` |
| `gzip: not in gzip format` | فك التشفير فشل | أعد الخطوة 2 |
| `Access denied` | بيانات الاتصال خاطئة | راجع `DATABASE_URL` في Railway |
| `SSL connection error` | نقص خيار TLS | أضف `--ssl-mode=VERIFY_IDENTITY` |
| `Unknown database` | القاعدة غير موجودة | أنشئها أولاً بـ `CREATE DATABASE` |

## ملاحظة عن الاحتفاظ

| المصدر | المدة |
|---|---|
| نسخة المزوّد التلقائية | **24 ساعة** — تنتهي في اليوم التالي |
| نسخ GitHub | **90 يوماً** |

أي بيانات أقدم من 90 يوماً لا يمكن استرجاعها. إذا احتجت مدى أطول، نزّل نسخة كل بضعة أشهر واحفظها خارج GitHub.
